* The machines
** Resource lifecycle R (a room) - a cycle (spec sec 2.2)
States =acquired, available, in-service, maintenance, out-of-order, retired=.
Initial =acquired=, sole terminal =retired=. The states =available, in-service,
maintenance, out-of-order= lie on cycles, for example =available -> maintenance ->
available=, so there is no sound wide-flag view. The projection is current_state
plus transition-legality.

| from         | event      | to           | writer             |
|--------------+------------+--------------+--------------------|
| acquired     | commission | available    | operator           |
| available    | check_in   | in-service   | party              |
| in-service   | check_out  | available    | party/operator     |
| available    | maintain   | maintenance  | scheduler/operator |
| out-of-order | maintain   | maintenance  | scheduler/operator |
| maintenance  | restore    | available    | scheduler/operator |
| out-of-order | restore    | available    | scheduler/operator |
| available    | fault      | out-of-order | operator           |
| in-service   | fault      | out-of-order | operator           |
| available    | retire     | retired      | operator           |
| maintenance  | retire     | retired      | operator           |
| out-of-order | retire     | retired      | operator           |

** Reservation lifecycle V (a booking) - a DAG with terminals (spec sec 2.4)
States =requested, held, confirmed, active, overdue, completed, cancelled,
expired, no-show=. The graph is acyclic. Its terminals are =completed, cancelled,
expired, no-show=. =overdue= is a live, non-terminal exit: it still holds the
room, and it ends at =check_out=.

| from              | event     | to                               | writer         |
|-------------------+-----------+----------------------------------+----------------|
| (none)            | request   | requested                        | party          |
| requested         | hold      | held                             | party          |
| requested         | cancel    | cancelled                        | party/operator |
| requested         | expire    | expired                          | scheduler      |
| held              | confirm   | confirmed                        | party          |
| held              | cancel    | cancelled                        | party/operator |
| held              | expire    | expired                          | scheduler      |
| confirmed         | check_in  | active                           | party          |
| confirmed         | cancel    | cancelled                        | party/operator |
| confirmed         | no_show   | no-show                          | scheduler      |
| active            | check_out | completed                        | party/operator |
| active            | overdue   | overdue                          | scheduler      |
| overdue           | check_out | completed                        | party/operator |
| confirmed, held   | reassign  | (unchanged; key := new instance) | operator       |

=check_in= and =check_out= are *shared events* of both machines, so the product is
synchronous: one event moves the booking and the room. =reassign= changes the
booking's resource key without changing its V state, so it is not a V edge.

** Coupling rule
LIVE = {held, confirmed, active, overdue}; AVAILABLE = {available, in-service}.
For every booking v bound to a room r, if v is LIVE then r is AVAILABLE.
=in-service= counts as reservable because an occupied room still carries live
bookings for later intervals.

- *C1* (at admission): =hold=, =reassign=, or a late-binding =check_in= onto a
  room outside AVAILABLE. The write side should have rejected it.
- *C2* (at the watermark): a live booking stranded on a room that left AVAILABLE
  on its own clock (a =fault= or =maintain=) with no compensation. Compensation
  is an operator =reassign=, an operator =cancel=, or the room returning to
  AVAILABLE.

** Interval invariant (interval scheduling)
*I7*: on each room, the booked intervals =[start, end)= of the LIVE bookings are
pairwise disjoint. It is checked at admission. It relates /two/ bookings that
share a key, so no per-entity flag or down-set can express it.

** Time axis
The fold takes no clock. Deadlines are policy constants. The *scheduler writes*
the event that discharges each deadline into the log:

| live state | deadline         | scheduler event | edge                 |
|------------+------------------+-----------------+----------------------|
| held       | hold.ts + 15 min | expire          | held -> expired      |
| confirmed  | start + 10 min   | no_show         | confirmed -> no-show |
| active     | end + 0 min      | overdue         | active -> overdue    |

The fold's only "now" is the *watermark*: the maximum event-time in the log.
*X1* reports a live booking whose deadline is at or before the watermark and has
no scheduler event. The fold reports that absence and never writes the missing
event.

** Fencing and late binding
- *F1*: each room keeps =fence= (initially 0), the highest token it has accepted.
  =check_in= must carry a token greater than the fence, and then sets the fence to
  it. =check_out= must carry the current fence. Any other token is fenced: the
  event is rejected, reported, and not applied.
- *Late binding*: a booking may be made against a class key (=small=) and bound
  to an instance at =check_in=. *B1* fires if the instance is not of the booked
  class. The view keeps =booked= (the key at request) and =key= (the current key).

* The log
=data/trace/reservation_log.csv= is in arrival order. Room and booking events
interleave, and each row is keyed by =resource=.

* Variants
- *Stretch: DHCP lease (RFC 2131, figure 5).* This is the tightest instance: a
  published state machine with explicit timers, a resource manager that can
  revoke, and no domain knowledge needed. The client states
  (INIT/SELECTING/REQUESTING/BOUND/RENEWING/REBINDING) map onto V. T1, T2 and
  lease expiry are scheduler events. "Conflict detected" (DHCPDECLINE) is R
  leaving AVAILABLE under a live lease, which is C2 and needs compensation. The
  stretch is to re-tell this fixture over an address pool.
- *Backward link: inventory allocation.* The picker's =allocated= state was
  already a reservation (spec sec 2.1 / challenge 01). A quantity-at-location
  is the resource, and the picker chain is one reservation's lifecycle. With
  several allocations against one on-hand quantity, I7 becomes a capacity sum
  instead of pairwise disjointness. The invariant is still cross-entity.
- *Downstream instance*: =aygp-dr/display-reservation=.

* The lesson
A reservation system is two machines plus time. Each machine alone is an
earlier rung: R is a cycle (sec 2.2) and V is a DAG (sec 2.4). The interval
invariant is new. It relates entities to each other over time, so the right
projection is per resource: the set of live intervals, both current_state
columns, and the coupling check. Time enters the log as scheduler-written
events, never as a clock argument to the fold.
